# Практическое задание: пункты 2–4

## Что подготовлено

Это вариант доработки репозитория MariaKhudiakova/cirrhosis-prediction.
В самостоятельный запускаемый пакет вынесен сценарий мультиклассовой
логистической регрессии. Исследовательские ноутбуки и результаты других
моделей сохранены; все модели из ноутбуков в пакет не перенесены.
Пункт 1 задания в эту работу не входит.

## 2. Рефакторинг кода ML-проекта

Код разделён по ответственности:

- `src/cirrhosis_prediction/data.py`: чтение исходных данных, проверка столбцов и целевой переменной.
- `src/cirrhosis_prediction/pipeline.py`: заполнение пропусков, кодирование категорий, масштабирование и классификатор.
- `src/cirrhosis_prediction/train.py`: разделение выборки, кросс-валидация, обучение, оценка, сохранение артефактов.
- `src/cirrhosis_prediction/predict.py`: загрузка сохранённого Pipeline и получение предсказаний.
- `configs/train.toml`: пути, seed, размер тестовой выборки, число фолдов и параметры модели.
- `tests/test_pipeline.py`: проверки сохранения/загрузки, новых категорий, входной схемы и обучения масштабирования отдельно на каждом фолде.

В отличие от исходного ноутбука, StandardScaler не обучается перед CV:
внутри каждого фолда обучается весь Pipeline. Тестовая выборка выделяется
до CV и используется для итоговой оценки фиксированной модели.
`id` и `Status` не попадают в признаки. Сохраняется весь Pipeline,
поэтому при предсказании используется та же предобработка.

Сценарий использует `data/raw_data.csv` и исходные метки C, CL, D.
Числовые признаки масштабируются, категориальные кодируются OneHotEncoder.
Это осознанное изменение по сравнению с ручным кодированием в ноутбуке:
старые значения метрик не следует выдавать за результаты нового сценария.
Исследовательские таблицы в README относятся к исходной работе.
Новые измеренные метрики записываются в `artifacts/metrics.json`.
Сохранённая модель обучена на тренировочной части; тестовая часть не
включается в последующее дообучение.

Это учебный пакет с базовыми практиками качества и воспроизводимости,
а не готовая медицинская система. В данных есть `N_Days` — длительность
наблюдения. Для задачи прогноза при первичном обращении необходимо отдельно
проверить доступность каждого признака на момент прогноза и пересмотреть
использование `N_Days`. Исправление утечки при масштабировании само по себе
не подтверждает пригодность датасета для клинического прогноза.

## 3. Poetry, pre-commit и линтеры

`pyproject.toml` содержит описание пакета, зависимости, dev-зависимости,
консольные команды и настройки инструментов. `poetry.lock` фиксирует
конкретные версии, а не только разрешённые диапазоны.

Инструменты:

- Black форматирует Python-код.
- isort упорядочивает импорты; профиль `black` согласован с Black.
- Flake8 проверяет стиль и некоторые ошибки кода.
- pre-commit запускает эти проверки при коммите.
- pytest запускает функциональные тесты.

Хуки локальные (`repo: local`, `language: system`) и вызывают
`poetry run ...`: версии линтеров берутся из окружения проекта и lock-файла.
Команда `poetry` должна быть доступна в PATH, в том числе при коммите из IDE.
Хуки проверяют Python-модули; `.ipynb` в эти проверки не включены.

## 4. Воспроизводимое виртуальное окружение в Git-проекте

В Git хранятся `pyproject.toml`, `poetry.lock`, `poetry.toml`,
`.gitignore` и инструкция установки. `poetry.toml` задаёт создание
окружения в `.venv` внутри проекта. Папка `.venv` исключена из Git.
Окружение восстанавливается командой `poetry install --with dev`.

Само виртуальное окружение не загружают в репозиторий: его содержимое
зависит от операционной системы и локальных путей. После каждого нового
клонирования нужно отдельно выполнить `poetry run pre-commit install`,
поскольку каталог `.git/hooks` также не переносится через Git.

Окружение этого пакета рассчитано на Python 3.11 или 3.12 и запуск нового
сценария логистической регрессии. Зависимости всех исторических ноутбуков
(например, CatBoost, XGBoost, LightGBM и библиотеки графиков) в это окружение
не входят. Пустой исходный `requirements.txt` не используется для установки.

## Как применить файлы к своему клону (Windows / VS Code)

1. Сохраните свои текущие изменения. Откройте локальную папку репозитория
   в VS Code и терминал PowerShell в корне проекта.
2. Создайте отдельную ветку:

```powershell
git switch -c practice/production-setup
```

3. Скопируйте содержимое папки `changes` из архива в корень проекта
   с заменой одноимённых файлов. README в архиве основан на скачанной
   версии репозитория: если ваш README уже изменён, перенесите новый
   раздел и обновление структуры вручную, сохранив свои правки.
4. Если Poetry ещё не установлен, установите его через pipx:

```powershell
py -m pip install --user pipx
py -m pipx ensurepath
```

Закройте и заново откройте VS Code, затем выполните:

```powershell
pipx install poetry==2.2.1
```

5. Выберите установленный Python 3.12 и установите зависимости:

```powershell
poetry env use 3.12
poetry install --with dev
poetry run pre-commit install
```

Если Python 3.12 не установлен, установите его или используйте имеющийся
Python 3.11 (`poetry env use 3.11`). Если уже активно другое окружение,
сначала откройте терминал без него. Для выбора интерпретатора в VS Code:
Ctrl+Shift+P → Python: Select Interpreter → `.venv\Scripts\python.exe`.

6. Проверьте и запустите проект из его корня:

```powershell
poetry check --lock
poetry run pytest -q
poetry run cirrhosis-train --config configs/train.toml
poetry run cirrhosis-predict --input data/raw_data.csv --output artifacts/predictions.csv
```

Последняя команда демонстрирует работу интерфейса на имеющемся файле,
а не оценивает качество на новых данных. В реальной работе передавайте
новый CSV с теми же признаками; столбец Status не требуется.
Порядок столбцов вероятностей определяется метками самой модели.
Загружайте через joblib только свои или доверенные артефакты.

7. Добавьте подготовленные файлы в индекс и проверьте pre-commit:

```powershell
git add src tests configs pyproject.toml poetry.lock poetry.toml .pre-commit-config.yaml .flake8 .gitignore README.md PRACTICE_2_3_4.md VALIDATION.md
poetry run pre-commit run --all-files
```

Если форматтер исправил файлы, повторите `git add` для исправленных файлов
и `poetry run pre-commit run --all-files`. Сообщение «files were modified»
при первом запуске форматтера означает, что изменения надо добавить заново.

8. Проверьте содержимое коммита:

```powershell
git diff --cached --stat
git status
```

В нём не должно быть `.venv`, `artifacts` или локальных файлов с секретами.
Затем выполните:

```powershell
git commit -m "Refactor ML baseline and configure Poetry and pre-commit"
git push -u origin practice/production-setup
```

Для push нужен доступ на запись в origin. Если репозиторий принадлежит
другому участнику и доступа нет, используйте собственный fork и создайте
Pull Request в исходный репозиторий. Не меняйте origin на чужой адрес.
После push откройте PR через GitHub и проверьте перечень изменённых файлов.
